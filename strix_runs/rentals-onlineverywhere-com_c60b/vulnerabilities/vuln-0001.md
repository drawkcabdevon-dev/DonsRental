# Business Logic Flaw: Return Date Before Pickup Date in /api/check-availability

**ID:** vuln-0001
**Severity:** MEDIUM
**Found:** 2026-08-27 19:49:04 UTC
**Target:** https://rentals.onlineverywhere.com
**Endpoint:** /api/check-availability
**Method:** POST
**CWE:** CWE-20
**CVSS:** 5.3
**Fix Effort:** Low

## Description

The /api/check-availability endpoint allows a returnDate that is chronologically before the pickupDate, yet still returns 'available: true'. This can lead to illogical bookings and incorrect availability calculations.

## Evidence

HTTP/1.1 200 OK\nContent-Length: 85\n\n{"available":true,"conflicts":[],"pickupDate":"2026-08-28","returnDate":"2026-08-27"}

## Impact

Incorrect availability calculations and potential for invalid bookings, leading to business disruption and customer dissatisfaction.

## Technical Analysis

The API endpoint does not properly validate the chronological order of pickupDate and returnDate. When a request is sent with returnDate < pickupDate, the system still responds with available:true, indicating a flaw in the business logic.

## Proof of Concept

1. Intercept a POST request to /api/check-availability.
2. Modify the JSON body to set 'returnDate' to a date before 'pickupDate'.
3. Send the modified request.
4. Observe the response, which will show 'available:true' despite the invalid date range.

```python
POST /api/check-availability HTTP/1.1\nHost: rentals.onlineverywhere.com\nContent-Type: application/json\n\n{"pickupDate":"2026-08-28","returnDate":"2026-08-27","vehicleId":"v1"}
```

## Remediation

Implement server-side validation to ensure that 'returnDate' is always chronologically after 'pickupDate'. Return an appropriate error message (e.g., 400 Bad Request) when this condition is violated.

## Assumptions

An attacker can manipulate the date parameters in the request.
